# proj3-apply-gate · 投递决策闸门

> **不是帮你多投，是帮你投得准。**
> GitHub 上同类项目全在比「谁投得多」，这个项目比的是「谁能证明自己的判断是对的」。

给系统一批岗位 JD 和你的真实简历，它输出三分类：**该投 / 不该投 / 边界**。

- 每一个「不该投」都必须引用 **JD 原文里触发的那句话** 当证据
- 每一份改写稿里的每个数字、年限、公司名，都必须能在 **你的原简历里找到出处**；找不到就回退重写，3 轮不过直接拦
- 连「性质有没有被抬档」都要查 —— 原简历写「完成流程」，改写稿不许写「已上线生产」
- 出稿前必须 **人工点头**，没点头在结构上就拿不到可投递稿

## 四个硬指标（实测，不是目标）

在 **57 题人工标注评测集**上跑出来的真实数字（2026-10-06，模型 `deepseek-flash`）：

| # | 指标 | 实测 | 目标 | 性质 |
|---|---|---|---|---|
| ① | 硬门槛漏放率 | **0.00%**（20 道硬门槛题，漏放 0 道） | = 0% | L1 门禁（纯代码） |
| ② | 事实可溯源率 | **100.00%**（26 篇放行稿 / 1301 个事实原子，0 篇被拦） | = 100% | L1 门禁（纯代码） |
| ③ | 未审批不放行率 | **0.00%** | = 0% | L1 门禁（图结构） |
| ④ | 三分类准确率 | **96.5%**（57 题） | ≥ 85% | L3 指标（不设门禁） |
| | └ 边界召回 | 71.4%（5/7） | ≥ 80% | **未达标，见下文** |

观测项（不设硬线）：误杀率 **0.0%**　单题成本 **¥0.0268**　单题耗时 **11.04 秒**　平均重写轮数 **1.00**

**评测跑的是固定档案 `data/eval_profile.json`，不是使用者自己的档案** ——
门禁要回答的是「代码有没有退化」，不是「使用者偏好有没有变」。理由与实现见下文「门禁跑固定档案」一节。

**①②③ 敢写「= 0」不是吹的，因为这三条根本不经过模型**：
① 硬门槛是词表 + 正则的纯 `if` 判断；② 溯源是规范化 + 匹配；③ 审批是图结构（没有 `resume` 就走不到 END）。
这三条都是带 exit code 的命令，可以每天重跑 —— 是门禁，不是承诺。

**② 的口径要写清楚**：分母是**最终放行的稿子**。跑满 3 轮溯源仍未通过的稿子会被拦下、不产出可投递稿 ——
那正是设计要的行为，把它们的原子算进分母等于在惩罚「正确拦截」。
被拦下多少篇单独报告（本轮 0 篇）。

### 边界召回没达标，这里如实说明

7 道边界题判对 5 道。判错的 2 道是 `jd-055` 与 `jd-059`：

- **jd-055**（JD 只有三行、条件全写成「面议 / 可谈」）：系统判了「该投」。**这道题的 gold 本身有争议** ——
  JD 写「熟悉 Python，对大模型应用有兴趣」，候选人完全符合，判该投在实用上说得通。
- **jd-059**（要求十万级以上用户量运维经验）：系统判了「不该投」。同样有争议 ——
  候选人简历有「保障线上调用稳定」的措辞但没有用户量数据，判「证据不足」和判「真实缺口」都讲得通。

**我没有为了让指标好看去改这两道题的 gold。** 如果只看口径无争议的 5 道，边界召回是 100%。
如实报 71.4%，是因为一个敢报「自己有一项没达标」的项目，比一个四项全绿的项目更可信。

## 30 秒看懂它凭什么敢承诺 0%

整个项目最重要的一条分工：

> **确定性的交给代码，模糊的才交给模型。**

| 判断类型 | 例子 | 交给谁 | 为什么 |
|---|---|---|---|
| 确定性 | JD 写「不提供工作签证」；要求 5 年经验你只有 1 年；要求 base 北京你在广州 | **纯代码 if + 词表** | 有唯一正确答案。交给模型只会引入幻觉，还白花钱 |
| 模糊 | 这段经历算不算「相关」；这个岗位是「表达缺口」还是「证据不足」 | **模型** | 本来就没有唯一答案，只有「讲不讲得通」 |

这条分工在代码里的体现：**硬门槛判死的岗位根本不进入打分与改写环节 —— 0 次模型调用、0 元成本。**
在 57 题评测里，25 道「不该投」的题一共花了 ¥0。

面试会问：「你既然叫 Agent，为什么还要写死这么多？」
**答：Agent 的价值在调度（该查什么、该改哪一段、该不该重试），不在判定。**
把判定交给模型，就等于放弃了三个「= 0」的承诺。自由度必须留在不影响判据的地方。

### planner 只调度，一个判断题都不做

```
用户: JD + 简历 → planner(模型) ──→ hard-gate(纯代码)   ← 硬门槛三档
                              ├──→ match-score(模型)     ← 对外三分类 / 对内五态
                              ├──→ tailor ⇄ provenance   ← 定向改写 + 溯源回退子图
                              ├──→ approval(interrupt)   ← 挂起等人点头
                              └──→ cost / report(纯代码) ← 记账 + 出稿 + 看板
                                    ↓
                            data/audit.db  ← 全链路唯一事实源
```

planner 的四条硬规则由**代码**强制，不靠提示词自觉：

1. **不许自己下判定** —— 判定值只从 `hard_result` / `match_result` 取
2. **不许跳过 provenance** —— 没拿到 `passed=true` 走不到 approval
3. **不许自己决定停** —— `rewrite_round >= 3` 由子图代码强制退出
4. **不许出成稿** —— `approval_status != approved` 时 report 只写草稿

省钱的一处设计：**候选动作只有唯一合法路径时不调模型**。
调度权交给模型的地方，是真正存在多个合理下一步的地方（例如改写策略选 project_first / experience_first / balanced）。

## 反编造的三层（A / B / C）

「反编造」全行业都在喊，但很少有人拆到第二层。

| 类 | 抽什么 | 判法 |
|---|---|---|
| **A 类** | 数字 / 百分比 / 金额 / 年限 / 人数 / 日期 / 公司名 / 学校名 / 职级 / 证书名 | 必须回原简历找到出处，找不到 → 拦 |
| **B 类** | 技术名词 / 工具名 | 允许来自 JD。**例外**：挨着「熟练 / 精通 / 主导 / 负责」而简历里没有 → 判编造 → 拦 |
| **C 类** | 状态 / 性质断言：上线 / 生产环境 / 已发布 / 服务 N 用户 | 与原简历的档位比大小，**升格就拦** |

**C 类是相对同类项目多做的一层。** 看这个例子：

> 原简历：「完成 Qwen3 法律领域 LoRA 微调流程与权重产出」
> 改写稿：「**已上线生产环境**」

A 类和 B 类在这里**全部通过** —— 每个名词都能找到出处。但性质从「技术验证」被抬成了「生产落地」。
简历造假里最常见、面试当场最容易被戳穿的就是这一种（「你说上线了，那线上多少人用？」）。

**判定不需要模型判断「像不像编的」**：

1. 从 `data/ledger.json` 的 `draft_stage_ceiling` 读改写稿允许的档位上限（人工标注、写了理由）
2. 抽改写稿里每个 C 类词，取它的档位（上线 = 生产落地档，完成流程 = 技术验证档）
3. **纯枚举比大小** —— 改写稿档位 > 上限 → 拦，报错原文「原简历为『原型/技术验证』，改写稿出现『上线』，越级」

实测（`python tests/run_unit_cases.py` 里的 `pv-004`）：
```
输入：负责企业知识库建设，已上线生产环境，服务 3000 用户。
输出：passed=False
  missed = ['已上线（性质升格：生产落地 > 原型/技术验证）',
            '生产环境（性质升格：生产落地 > 原型/技术验证）',
            '服务 3000 用户（性质升格：生产落地 > 原型/技术验证）']
```

还有一道 **只读母版 guard**：改写稿输出路径指向 `data/profile/resume.md` → 直接抛错。
原简历是溯源的唯一对照物，顺手把它也改了，「找出处」就变成自证循环，指标②直接失效。

## 不只是打分：逐条告诉你这份 JD 该怎么改简历

「该不该投」只是第一问，第二问是**该怎么改** —— 所以走完改写环节的岗位会额外产出一份
`rewrite_guide.md`（网页工作台里是「怎么改简历」tab），把 JD 一条条拆开对照：

| JD 要什么 | 你简历里有什么 | 该怎么改 | 状态 |
|---|---|---|---|
| 引用溯源与拒答机制实现 | 「可信回答机制：回答强制标注引用来源（文档名 + 原文链接）…」 | 小标题换成 JD 原词，面试要能说清引用怎么带出来的 | 可强化 |
| Milvus / FAISS 等向量库经验 | *（简历里没有）* | **别编** —— 要么补一个真跑过的 demo，要么面试如实说明 | 真实缺口 |
| 本科及以上学历 | 「2021.09 - 2025.06　大连科技学院　交通工程专业　本科」 | 已满足；非科班建议保留「自学课程」一行 | 已覆盖 |

三档状态由代码强制（`已覆盖` / `可强化` / `真实缺口`），并且**每条声称的「简历素材」都要回原文核对**：

- 素材核不上 → 整条降级为「真实缺口」，并**把那段素材抹掉不展示**（不给使用者一个不存在的素材）
- 没给素材却说「已覆盖 / 可强化」→ 自相矛盾，同样降级
- 素材确有出处却判了缺口 → 上调为「可强化」（不能低估自己）
- `jd_quote` 核不上 JD 原文 → 标记 `quote_verified=False`，页面显示警告

**为什么这层核对必须有**：这里最容易犯的错不是漏写，是「帮你编」。
模型很乐意替你润色出一条没做过的经历 —— 写进简历，面试一问就穿。
核对实现与溯源共用同一份 `core.atoms.match_in_text`，一份实现两处用。

处方**不需要审批**：它不是可投递稿件，而是给你看的指导材料；审批管的是 `resume.md` / `cover_letter.md` 这两个成品。

## 两组对照实验

同类项目几乎没人做对照实验。这两张表是「会做实验」和「会写功能」的区别。

### 实验一 · 溯源校验到底有没有用

分层抽样 15 题（不该投 / 该投 / 边界各 5 道），A 组带溯源回退，B 组同一套提示词但不校验直接出稿：

| 组 | 链路 | 编造率 | 性质升格率 | 平均轮数 | 单题成本 |
|---|---|---|---|---|---|
| **A** | `tailor → provenance →（不过就回退重写）` | **0.00%** | 0.00% | 1.13 | ¥0.01755 |
| B | `tailor` 直接出稿，不校验 | 0.41% | 0.00% | 1.00 | ¥0.01304 |

**结论**：溯源回退把编造率压到 0，代价是单题成本高 34.5%（多出来的钱就是回退重写的钱）。
这个差价就是「溯源校验」这个功能的价格标签。

### 实验二 · 多节点 vs 一个大 prompt 一把梭

同一批 15 题，A 组是本项目，B 组是一个大 prompt 让模型一次输出三分类 + 改写稿：

| 组 | 做法 | 三分类准确率 | 硬门槛漏放率 | 单题成本 | 单题耗时 |
|---|---|---|---|---|---|
| **A** | 确定性硬门槛 + 五态分类 + 子图改写 | **93.3%** | 0.0 | **¥0.01056** | 7.85s |
| B | 一个大 prompt 一次输出全部 | 66.7% | 0.0 | ¥0.01157 | 7.87s |

**结论（含诚实的代价说明）**：

- **准确率差 26.6 个百分点**，差距全部来自边界题 —— A 组 5 道判对 4 道，B 组 5 道全判成「该投」。
  也就是说：**给了清单的大 prompt 也能判对简单题，真正分不出高下的是「信息不足时该不该猜」。**
- **成本上多节点反而更便宜**（0.91 倍）。原因不是模型省了，是**硬门槛判死的岗位不进入模型环节**：
  15 题里有 5 道是硬门槛题，A 组在这 5 道上花了 ¥0。这是「确定性的交给代码」直接兑现成钱。
- **硬门槛漏放率两组都是 0.0 —— 这一项没能区分开**。因为 B 组的 prompt 里我明确给了硬门槛清单，
  模型照着清单也能报对。**但两者的抗退化能力不同**：A 组删掉一条规则 `gate.py` 立刻变红；
  B 组改一次 prompt 就可能悄悄漏掉一条，而且没人会发现。这一条是设计差异，不是单次实验能测出来的。

## 三层门禁：为什么这么分

| 层 | 是什么 | 跑什么 | 怎么判 | 改什么之后重跑 |
|---|---|---|---|---|
| **L1** | 确定性门禁 | `gate.py` 跑 20 道硬门槛题 + 四项矛盾检查 | **exit 0，必须 100%** | 改 `rules.json`、改正则、改 hard-gate 代码 |
| **L2** | 结构校验 | `validate_ledger.py` + `validate_eval_set.py` | **exit 0，必须 100%** | 改账本、改评测集 |
| **L3** | 模型行为指标 | `eval/run.py` | **只出数字，不设门禁** | 改 prompt、换模型 |

分界的判据是一句很硬的话：**受模型影响的东西不适合当门禁，只能当指标。**

混着跑的直接后果：你改了一行正则导致准确率波动，分不清是正则的锅还是模型随机性的锅，
然后就会去调提示词，把本来正确的东西调坏。

四项**跨字段矛盾检查**（v1 完全没有这一层，它只查「字段有没有」，不查「两个字段有没有互相打脸」）：

| 检查 | 不过时 |
|---|---|
| 判了 reject 但 `verdict_reasons` 里引文为空 | FAIL |
| 引文不是 JD 原文的子串 | FAIL |
| `rule_id` 不在 `rules.json` 词表里 | FAIL |
| 判 reject 但既无硬依据也无软扣分依据 | WARN |

**L1 同时也是数据质量的验收**：20 道硬门槛题必须 100% 命中 ——
这个数字就是「规则词表写全了没有」的判定标准。词表不全的表现只有两种（漏放 / 误杀），两种都能被同一个门禁抓到。

### 门禁跑「固定档案」，不跑使用者自己的档案

这是实测踩出来的设计修正。评测集的 gold 标注时假设「期望城市 = 广州」，
而使用者把档案改成「上海」之后，一道 `base 上海` 的硬门槛题就不再构成冲突 ——
**这是正确行为**（上海确实在他期望城市里），但门禁却报**漏放率 5.0%**、`exit 1`。

问题不在判定，在于**门禁把两件事混在了一起**：

| 门禁该回答的问题 | 不该被它回答的问题 |
|---|---|
| 代码有没有退化？规则词表还全不全？ | 使用者的偏好有没有变？ |

所以现在分成两份档案：

| 档案 | 谁用 | 内容 |
|---|---|---|
| `data/profile/candidate_profile.json` | **生产路径**（`main.py judge` / 网页工作台 / MCP） | 使用者的真实档案，随他改 |
| `data/eval_profile.json` | **评测与 L1/L3 门禁** | 固定值，与评测集 gold 的标注口径一致 |

实现是环境变量 `PROJ3_PROFILE` 覆盖 + `cfg.use_eval_profile()`（`eval/run.py`、`eval/compare.py`、`scripts/gate.py` 开头各调一次）。
生产路径不设这个变量，用的就是真实档案。

**这条值得单独说**：门禁一旦会「跟着人的偏好漂移」，它就不再是门禁了 ——
红的时候你得先判断「是代码坏了还是我改了个数」，那这个红灯就废了。

## HTTP 接口与 MCP Server

### FastAPI（`server.py`）

```
GET  /health                 健康检查（规则版本 + 各表行数）
POST /judge                  提交 JD 判定（可能挂起等审批）
GET  /approvals              待办列表
POST /approvals/{ticket_id}  批准 / 驳回
GET  /sessions/{thread_id}   查会话状态（是否真挂着）
GET  /judgements             历史判定记录
GET  /cost                   成本汇总
```

审批接口做**三道关**，顺序不能换：

| 关 | 校验 | 不过时 |
|---|---|---|
| 1 | 待办表里有没有这个单号 | 404 |
| 2 | 会话是不是**真的**挂在挂起态（查图状态 `next` 非空） | 409 |
| 3 | 单号绑定的 `thread_id` 与请求的是不是同一个 | 409 |

**第 2 关最关键。** 往一个「其实已经不在挂起态」的会话传普通输入，中断状态会**静默丢失** ——
`next` 变空、`__interrupt__` 消失、**还不报错**，审批单就这么没了。
所以在接口层必须先查会话是不是真挂着，不能只看待办表。

实测（`python tests/run_unit_cases.py approval-gates`）：重复批准 → 409，不存在的单号 → 404。

### 自研 MCP Server（`mcp_server.py`）

不是只当 MCP 客户端，是自己写 Server，把硬规则引擎暴露给任何 MCP 客户端：

| 工具 | 作用 |
|---|---|
| `check_hard_rules_tool(jd_text)` | 跑硬规则引擎，返回判定 + 命中的 rule_id + JD 原句引文 |
| `explain_rule(rule_id)` | 查某条规则的完整定义（触发词 / 排除词 / 边界声明） |
| `list_rules()` | 列出全部规则（按三档分组） |

全程不调模型 —— 硬规则本来就是确定性的，走 MCP 也一样不花钱。

## 开发中修掉的三个真 bug（都不是模型的问题）

留这一节是因为「改了什么、为什么改」比「现在看起来多干净」更能说明问题。

### bug 1：算出来的东西没落库 = 没算

工作台的「视图 4 · 溯源对比」和「视图 6 · 审计时间线」打开是白的。
链路排查：`report_node` 把完整字段交给了 `save_judgement`，但**落库的 INSERT 只写了列表页要的 20 个字段**，
漏掉 `resume_base` / `draft_lines` / `atoms` / `evidence_map` / `missed` / `audit_trail`；
而 `build_snapshot.py` 里这 6 个字段还是**硬编码的 `[]`**。两头都缺，视图自然空白。

- 修法：表加 8 列 + 加**幂等迁移**（`CREATE TABLE IF NOT EXISTS` 不会给已存在的表加列，必须 `PRAGMA table_info` + `ALTER TABLE`）+ 落库改成列名字典驱动（避免再漏）
- 教训：**视图是白的，先查数据源，别怀疑模板**

### bug 2：规范化两边没拿同一把尺子

`jd-026` / `jd-046` 跑满 3 轮溯源都过不了，拦下的理由是「Function Calling（能力断言 + 简历无此技术 = 编造）」——
可简历技能栈里**明明写着 Function Calling**。
根因：原子做规范化时传了 `synonyms=False`，而简历那边是 `synonyms=True`。
同义词表把简历里的 `Function Calling` 转成了 `function-calling`，原子却还停在 `function calling` ——
**两边不在同一个字符串空间里，必然匹配不上**。

- 修法：两边统一 `synonyms=True`；加回归用例 `pv-011`（原样引用必过）/ `pv-012`（真编造 `Kafka` 仍必拦）
- 教训：**规范化不是「谁更干净」，是「两边用同一把尺子」**
- **修复效果是可量化的**：平均重写轮数 **1.23 → 1.00**，单题成本 **¥0.0109 → ¥0.0092**（降 16%）。
  也就是说修之前，**每 4 道题就有 1 道在无效重写** —— 简历里明明有的能力被判成编造，改 3 轮也改不对。
  这类「指标一直是绿的、但一直在悄悄烧钱」的 bug，只有把成本当成一等指标才看得见。

### bug 3：「告诉你该怎么改简历」这件事，压根没做

这是使用者最直接的反馈：**判定页有打分、有理由、有「缺什么信息」，唯独没有「所以简历该怎么改」。**
排查发现两层问题：

1. `changes`（改写员自己写的「做了哪些重排重述」）一直在算，但**只写进了 `verdict.md`，没落库** ——
   页面取不到。**算出来的东西不落库 = 没算**，和 bug 1 同一个病根，这是第 3 次犯。
2. 更深的一层：`changes` 是流水账（「顺序重排：把项目经历提到前面」），
   **根本不是「JD 这条要求 → 你简历里的哪句 → 该怎么写」的逐条对照**。这个能力当时确实不存在。

- 修法：新增结构化输出 `jd_mapping`（`jd_requirement` / `jd_quote` / `resume_evidence` / `suggestion` / `status`）
  + 代码核对 `verify_mapping()`；表加 3 列 + 幂等迁移；接进网页工作台（第 4 个 tab）与离线看板（第 7 个视图）；
  并把 `/judge` 接口的返回值、`rewrite_guide.md` 一并补齐。
- 教训：**「算出来了」和「用户看得到」之间还隔着落库、转换、渲染三道关**；
  而且**界面没有的字段，往往是能力本身没有**，不只是显示问题。
- 顺带收敛了一处重复实现：这张处方要判断「你简历里到底有没有这句素材」，和溯源判断「改写稿有没有编造」
  是同一个判定 —— 于是把它提升为 `core.atoms.match_in_text()`，溯源与处方共用一份。
  **同一条链路有两份实现，迟早有一份是错的**（项目里已经因此踩过 4 次）。

| 5 | **FastAPI 不能开 `--workers 2`** | 多 worker 会出现 `database is locked` | `SqliteSaver` 与 `audit.db` 的锁都不跨进程；要并发得上 PostgresSaver |

| 7 | **简历账本里有 2 条「待确认」主张** | 万涵云信、上海燊醒两段工作经历的表述未经本人核实 | `ledger.json` 的 `verification_status` 字段标着，对外使用前必须核实 |
| 8 | **不做爬虫、不填表、不提交** | 这是设计边界，不是缺陷 | 自动提交是唯一会被平台封号的动作，且要不断维护页面元素 |

## 成本与价格出处

成本按 **DeepSeek 官方的高峰 / 空闲两档**分别计费，不是取平均：

| 时段 | 时间 | deepseek-flash 输入（未命中缓存） | 输出 |

| 高峰 | 工作日 9:00-12:00、14:00-18:00 | ¥2 / 百万 tokens | ¥8 / 百万 tokens |

**出处**：https://api-docs.deepseek.com/zh-cn/quick_start/pricing （2026-10-06 读取）
价格以官方页面为准，`core/llm.py` 里只是本地副本；官方调价后改那张表或 `.env` 覆盖，不用动业务代码。

实测单题成本 **¥0.0268**（57 题合计 ¥1.53）。

**成本为什么比早期版本涨了**：加入「逐条改写处方」（12 条 × 每条约 150 字）后，
单题成本从 ¥0.0092 → **¥0.0268**（约 2.9 倍），单题耗时 6.99 → 11.04 秒。
**模型调用次数完全没变（仍是 3 次/题），涨的全是输出 token。**
这是这个功能的真实价格标签，不藏着 —— 换来的是使用者真正要的那份东西：
不是「该不该投」，而是「该怎么改」。

**另外记一条实测坑**：`deepseek-flash` 默认**开启思考模式**，而思考模式**不支持 `tool_choice`** ——
直接调 `with_structured_output` 会报 400 `Thinking mode does not support this tool_choice`。
本项目在构造客户端时显式关闭思考模式（`extra_body={"thinking": {"type": "disabled"}}`），
顺带解决两件事：`temperature` 才生效（五态判定才稳定）、省掉 reasoning token 的费用与等待。
出处：https://api-docs.deepseek.com/zh-cn/guides/thinking_mode
