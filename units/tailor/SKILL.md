# units/tailor · 定向改写 + 逐条改写处方

## 我负责什么

针对一个具体 JD，产出三份东西：

1. **定制简历**（`output/<jd_id>/resume.md`）—— 需审批后才写出
2. **招呼语 / 求职信**（`output/<jd_id>/cover_letter.md`）—— 需审批后才写出
3. **逐条改写处方**（`output/<jd_id>/rewrite_guide.md`）—— **不需要审批**，它告诉你「这份 JD 该怎么改简历」

改法只有两种：**重排顺序**、**重述措辞**。就这两种。

## 逐条改写处方（jd_mapping）

第 3 份产出是使用者最常要的答案：**别只告诉我该不该投，告诉我该怎么改**。
每条处方回答三件事：

| 字段 | 含义 | 怎么被核对 |
|---|---|---|
| `jd_requirement` | JD 的这条要求（一句话提炼） | — |
| `jd_quote` | 支撑它的 JD 原句 | **必须能在 JD 原文里逐字找到** |
| `resume_evidence` | 你简历里对应的素材原句 | **必须能在简历原文里找到**，找不到就留空 |
| `suggestion` | 建议怎么写 / 或者为什么不能写 | — |
| `status` | `已覆盖` / `可强化` / `真实缺口` | 三值枚举，代码强制 |

**这里最容易出的错不是漏写，是「帮用户编」。** 模型很乐意替用户润色出一条没做过的经历，
写上简历面试一问就穿。所以 `verify_mapping()` 会拿 `resume_evidence` 回简历原文核一遍：

- 核不上 → 整条**降级为「真实缺口」，并把那段素材抹掉**，不展示给使用者
- 没给素材却说「已覆盖 / 可强化」→ 自相矛盾，同样降级
- 素材其实有出处却判了「真实缺口」→ 上调为「可强化」（不能低估自己）
- `jd_quote` 核不上 → 标记 `quote_verified=False`，页面显示警告

一句话：**宁可少告诉用户一条「可以这样写」，也不能给一条不存在的素材。**

## 我的红线（写进 system prompt，由代码在下一环兜底）

| 允许 | 禁止 |
|---|---|
| 把最相关的项目提到前面 | 新增任何原简历里没有的数字 / 年限 / 公司名 / 日期 |
| 换掉与这个 JD 无关的措辞 | 新增任何原简历里没有的技术名词（尤其是「熟练 X」这种能力断言） |
| 把简历里已有的事实用更贴 JD 的词重述 | 把性质升格（原简历「完成流程」→ 不许写「已上线生产」） |
| 从经历库卡片里挑最相关的重组 | 编造经历库之外的任何内容 |

**这条红线不是靠自觉，是靠 `provenance` 代码兜底。** 我写的每一句都会被拆成事实原子逐个回原简历核对，
核不上就带着「哪几项没出处」打回来让我重写（最多 3 轮）。所以我不是「被要求不要编」，是「编了过不了门」。
处方里的 `resume_evidence` 走的是**同一套核对实现**（`core.atoms.match_in_text`）。

## 输入

- JD（含原文）
- `match-score` 的五态结论与分项分
- 原简历全文（**只读，不许改**）
- 经历库卡片（重组的素材来源）
- 简历路由（投哪一版、改写重点是什么）
- 上一轮的 `missed` 清单（如果是重写轮）
- 当前重写轮数（上限 3，由代码强制）

## 不归我管的

- 我不判断该不该投（那是 hard-gate 与 match-score 的事）—— 判「不该投」的岗位我根本不会被调用
- 我不做溯源校验（那是 provenance 的事，我自查不算数）
- 我不决定稿件能不能出（那是 approval 的事，没人工点头拿不到可投递稿）
- 我不提交到招聘平台（这是项目红线，**永远不做**）

## 错误策略

| 情况 | 行为 |
|---|---|
| 模型输出不合 schema | 重试 1 次；仍失败**直接报错，不产出半成品** |
| 模型返回空文本 | 抛 `TailorError` —— 宁可不出稿，不许出残稿 |
| 被 provenance 打回 | 带着 missed 清单重写，轮数 +1 |
| 第 3 轮仍不过 | 退出循环，标 `verify_failed`，落库交人工 |

## 自己的用例

`cases.json` —— 故意塞假数字的、故意把「技术验证」写成「已上线」的、正常改写的各一组。
前两组必须被下游 provenance 抓到，这是本单元与 provenance 的联合用例。
