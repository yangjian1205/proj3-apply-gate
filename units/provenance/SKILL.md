# units/provenance · 溯源校验（反编造）

## 我负责什么

**改写稿里的每一个事实，都必须能在原简历里找到出处。** 找不到就不放行，带着「哪几项没出处」回退给 tailor 重写。

三类原子，三种判法：

| 类 | 抽什么 | 判法 |
|---|---|---|
| **A 类** | 数字 / 百分比 / 金额 / 年限 / 人数 / 日期 / 公司名 / 学校名 / 职级 / 证书名 | 必须能在原简历里找到出处，找不到 → 拦 |
| **B 类** | 技术名词 / 工具名 | 允许来自 JD。**例外**：若紧挨着「熟练 / 精通 / 主导 / 负责 / 落地」而简历里没有 → 判编造 → 拦 |
| **C 类** | 状态 / 性质断言：上线 / 生产 / 已发布 / 已交付 / 服务 N 用户 | 与原简历的档位比大小，**升格就拦** |

## C 类是本项目相对同类项目多做的一层

看一个例子：

> 原简历：「完成 Qwen3 法律领域 LoRA 微调流程与权重产出」
> 改写稿：「**已上线生产环境**」

v1 的两类原子在这里**全部通过** —— 每个名词都能找到出处。但性质从「技术验证」被抬成了「生产落地」。
简历造假里最常见、面试当场最容易被戳穿的就是这一种（「你说上线了，那线上多少人用？」）。

**我的判法不需要模型判断「像不像编的」**：
1. 从 `data/ledger.json` 的 `draft_stage_ceiling` 读改写稿允许的档位上限（人工标注，有理由）；
2. 抽改写稿里每个 C 类词，取它的档位（上线=生产落地档，完成流程=技术验证档）；
3. **纯枚举比大小** —— 改写稿档位 > 上限 → 拦，报错原文「原简历为『原型/技术验证』，改写稿出现『上线』，越级」。

全程没有一次模型调用。这就是「确定性的交给代码」在溯源层的应用。

## 只读母版 guard

改写稿的输出路径**指向 `data/profile/resume.md` → 直接抛错**。
理由：原简历是溯源的唯一对照物。顺手把它也改了，「找出处」就变成自证循环，硬指标②直接失效。

## 不归我管的

- 我不判断改写稿写得好不好（那是 tailoring 质量，不在指标里）
- 我不修改写稿（那是 tailor 的事，我只给 missed 清单）
- 我不判断事实是否「重要」—— 一律同等对待，一个数字和一处职级同样拦

## 错误策略

| 情况 | 行为 |
|---|---|
| 找不到出处 | 带 `missed` 清单回退给 tailor 重写，**最多 3 轮** |
| 第 3 轮仍不过 | 不出稿，标 `verify_failed`，落库交人工裁定（**这是正确行为，不是失败**） |
| 输出路径指向母版 | 抛 `ProvenanceError`，一个字都不写 |
| 同义词/全半角/中文数字差异 | 先规范化再匹配（「约 3 年」= 「3 年」，「LANGGRAPH」=「langgraph」） |

## 自己的用例

`cases.json` —— A / B / C 三类各一组正反例：
- A 类：真数字能过、假数字必拦
- B 类：普通技术名词放行、紧挨能力断言且简历没有的必拦
- C 类：平级表述放行、升格表述必拦
- 路径：指向母版必抛错
