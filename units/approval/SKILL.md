# units/approval · 审批门

## 我负责什么

**没有人工点头，就产不出「可投递」的稿子。** 不是「建议你检查」，是结构上就出不来。

实现靠两件事：
1. **图结构**：`interrupt()` 挂起 —— 没有 `resume` 就永远走不到 END。
2. **产物扫描**：成稿里出现 `pending` / `待补` / `verify_failed` / `TODO` 字样 → 直接 FAIL。

硬指标③（未审批不放行率 = 0%）由本单元守。

## 三道关（直接复用 proj2 的教训）

审批接口收到请求后，必须依次过三关，**顺序不能换**：

| 关 | 校验 | 不过时 |
|---|---|---|
| 1 | 待办表里有没有这个单号 | `404` |
| 2 | 会话是不是**真的**挂在挂起态（查图状态 `next` 非空） | `409` |
| 3 | 单号绑定的 `thread_id` 与请求的是不是同一个 | `409` |

**第 2 关是最关键的那一道。** proj2 踩过的坑：往一个「其实已经不在挂起态」的会话传普通输入，
中断状态会**静默丢失** —— `next` 变空、`__interrupt__` 消失、**还不报错**，审批单就这么没了。
所以在接口层必须先查会话是不是真挂着，不能只看待办表。

## 一条反直觉的设计

**审批状态以 `data/audit.db` 为准，不以看板快照为准。**
快照只是某一刻的照片，服务可能重启过，会话早就不在挂起态了。
所以看板上显示「待审批」不等于后端真挂着 —— 批准动作必须走接口重新确认，
绝不允许读快照判断，更不允许把审批结果写回本地存储（例如浏览器 localStorage）。

这是指标③在界面侧的防线。

## 不归我管的

- 我不判断稿子写得好不好（那是人的事，我只负责让他必须看）
- 我不替人做决定 —— 拒绝就走 `reject` 分支落库，本次不出稿

## 错误策略

| 情况 | 行为 |
|---|---|
| 单号不存在 | 404，不透露会话信息 |
| 会话不在挂起态 | 409，提示「会话未处于挂起状态，请重新发起判定」 |
| 单号与会话不匹配 | 409 |
| 人拒绝 | 落库 `rejected` + 理由进审计表，**不出稿** |
| 产物扫描命中黑名单词 | FAIL，不许标记为可投递 |
