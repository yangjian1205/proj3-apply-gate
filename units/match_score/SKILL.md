# units/match-score · 匹配打分与五态分类

## 我负责什么

把「简历 vs JD」变成一个**对内五态**的判断，并给出多维分项：

| 五态（对内） | 判定条件 | 映射到对外 |
|---|---|---|
| 已匹配 | 硬门槛全过 + 软条件大部分命中，有可展开的证据 | 该投 |
| 表达缺口 | 硬门槛全过，但**简历没写清** JD 要求的某项能力（本人其实做过） | 边界 |
| 证据不足 | 材料暗示可能具备，但撑不起对外表述 | 边界 |
| 真实缺口 | 事实明确不满足，且能引用 JD 原句 | 不该投 |
| 待确认 | 缺决定性信息（JD 没说地点、没说是否远程） | 边界 |

分项：`relevant`（相关度）/ `level`（职级）/ `skill`（技能覆盖），各 10 分制。

## 两条设计上最关键的事

**① 我只输出五态，不输出三分类。**
三分类由代码常量 `core/config.py: STAGE_TO_VERDICT` 映射。
为什么：口径升级不改对外契约。如果让模型直接输出「该投 / 不该投 / 边界」，
「表达缺口」这类有信息量的细分就丢了，而且映射规则会漂移。

**② 我负责守住「表达缺口」这条线，它就是误杀率的守门员。**
v1 把「该投但简历没写清」和「信息不足」都塞进一个 borderline，结果转行者被系统性误杀。
两者的证据来源必须分开：
- **表达缺口**锚点：JD 要求的能力**出现在简历的职责描述里，但没进技能栏** —— 可匹配的结构特征
- **待确认**锚点：**JD 原文根本没提**这项条件 —— 完全不同的证据来源

## 不归我管的

- 硬门槛冲突（签证 / 户籍 / 坐班城市 / 学历 / 证书 / 应届 / 语言 / 年限阈值）→ 那是 hard-gate，纯代码，我只是转述它的结论
- 改写简历（那是 tailor）
- 事实有没有出处（那是 provenance）
- **职级措辞不参与是否投递的判断**，只影响 `level` 分项扣分

## 错误策略

| 情况 | 行为 |
|---|---|
| 模型返回的 stage 不在五态枚举里 | 校验失败 → 重试 1 次 |
| 重试仍不合 schema | **降级成「待确认」交人工**，绝不猜一个分类 |
| 分项超出 0—10 | 夹到边界并记一条告警 |
| 缺 API key | 抛 LLMError，拒绝给出判定 |

## 自己的用例

`cases.json` —— 五态各一组正反例，外加「表达缺口 vs 待确认」的对照。
这一对最容易互相污染，也是本单元最值得测的地方。
